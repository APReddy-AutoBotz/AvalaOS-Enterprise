# AvalaOS Enterprise: agent brief

Read this file and the one work-package spec you were given. Nothing else is required reading.

## Product goal

A working, reviewable journey for one business process:

supported source documents → editable assessment → useful BRD / PDD / FRD / SDD and As-Is / To-Be flows → reviewed work proposals → persistent Delivery board items.

## The six behaviours that define "done"

1. One Assess experience and one current assessment per process. One current document per selected type. Engine, schema, handoff and record versions appear only in History. Approved revisions are preserved and clearly distinct from the working draft.
2. Ingest real transcript, SOP and flowchart content. Show source references, missing information and uncertainty. Users can edit extracted fields and steps; edits persist and drive assessment and documents.
3. Recommend at process and step level. Support "AI unnecessary", API-first where an API is confirmed, and human judgment where it belongs. Explain reasons and alternatives.
4. Generate useful, distinct BRD / PDD / FRD / SDD and editable flows. Preserve user edits. When inputs change, mark dependent outputs "needs review" and let the user choose. Missing design facts stay explicit questions or proposals.
5. Generate actionable work-item proposals with descriptions, acceptance criteria and requirement links. Owner, estimate and dates may be unassigned. Document headings are never work items.
6. Users review, edit and select proposals before confirming. Confirmed items appear once on the normal Delivery board and keep status and detail updates.

## Rules that always apply

- **Invent nothing.** No default, sample or "baseline" content in a user's model or document. No assumed API, policy, cost, ROI, volume or evidence. Unknown stays unknown and becomes an open question.
- **One model.** The Process Model is the single source for assessment, documents, flows and proposals. Do not add a second representation of a process.
- **No internal labels in primary views.** Version numbers, hashes, schema names and PR numbers belong in History only.
- **Pure domain first.** Logic goes in `domain/` with no I/O and no React, with unit tests. Then the server command. Then the UI.
- **Server holds secrets.** AI provider keys and service-role keys never reach the browser or the repository.
- **Small pull requests.** One work package per pull request, with its tests. Do not add governance, evidence or status documents.

- anything that would write generated default content.

## Tests

- Test what the change can break, not everything every time.
- New code gets fast `node:test` tests beside it (`*.test.ts`), run by `npm run test:new`. Database rules are checked by the SQL files in `supabase/tests/`.
- The inherited unit tests (`npm run test:unit`) run in CI only when inherited code, its runners or the dependencies change. Do not add to them.
- When inherited code is retired, delete its tests in the same pull request.

## Definition of done for a pull request

- The "Done when" line of the work package is covered by tests that fail before the change and pass after.
- Typecheck, the tests relevant to the change, and `npm run build` pass in CI.
- No rule in "Rules that always apply" is broken.
- The pull request description says what changed, how it was verified, and what was not verified.

The instructions tell the AI to say facts with ids starting `h:` as how Avala OS works, never as the process's record. The measure fails an answer with no direct answer first. Live only once `journey-ai` is deployed with this task (approved by the owner, bundled with the board scope). When the record does not answer, the panel says what is missing. On the board (`domain/assistant/board.ts`, task `askBoard`): `boardFacts` builds the facts by rule from what the board page reads (items, sprints, people by name, processes by name): counts by status, kind and owner, what is blocked, on hold, overdue or has no owner (said as "none" when there is none, so the AI never guesses an absence), the active and planned sprints with goal, dates and progress (completed ones only counted), the backlog, and each item with only what is set (at most `BOARD_LIMITS.items`, what needs attention and what the question names first, with a count of the rest); plus `PLATFORM_FACTS`. Its instructions are the process task's, line by line, with its own line on what the segments are and without the assessment line; same schema and answer shape. On the whole workspace (`domain/assistant/workspace.ts`, task `askWorkspace`): `workspaceFacts` builds, by rule, the counts (processes and where they stand, the split of steps across assessed processes, open questions, proposals waiting, processes with no analyst, architect or approver named), the portfolio order with hours and the 80/20, one summary per process (`WorkspaceProcess`: status, who is named, what is open, the assessment in short, its place, its applications; at most `WORKSPACE_LIMITS`, those the question names first), the applications list (with which processes use each, `matchApplication`), the people by name and access (never email addresses) and each board in short (its `boardFacts` counts). A process's own record (`askFacts`) joins only when the question names exactly one process (`namedProcess`); its facts open inside that process (target `within`). Workspace facts lead to the process, the applications list, People or the processes page. The workspace subject reads everything through the store, so a person is answered only from what they can read. Follow-up questions: the last two answered turns go along as `context:` segments (`earlierSegments`), which the instructions say never to cite or answer from, and `readAnswer` drops any sentence citing one; closing the panel forgets them. `followUps` takes the scope, so the board and the workspace never suggest a question about "this process". What is asked about is an `AskSubject` (`journey/process/askSubjects.ts`: `processSubject`, `boardSubject`, `workspaceSubject`: how the record is read, the facts, the task, the starter questions); `AskPanel` takes one and is the same for both. Nothing is stored or changed; the AI use shows under "Ask Avala". The in-browser store has no AI, so the panel says answers need the server. Test: `domain/assistant/ask.test.ts`, `tests/e2e/assistant.spec.ts`. The measure (`eval/ask/`, `eval/README.md` "Ask Avala measure"): 66 questions on the sample case in the plan's seven kinds (`questions.json`, with the planted instruction passages that exist only there), read through the same record as the panel (`journey/process/askRecord.ts` `loadAskRecord`, shared by `AskPanel` and `eval/ask/sample.ts`) and scored by rule (`scorer.ts`: `judge` per kind, `scorecard` against the plan's targets, tokens per question, names and numbers in no fact). `node eval/ask/run.ts` lists the set without AI; a live run is the GitHub workflow "Ask Avala measure" (`.github/workflows/ask-eval.yml`: "Run workflow", or `[ask-eval]` in a commit message on a `claude/` branch), which calls `journey-ai` as a trusted server and counts the AI use against the workspace named "Avala check". Run it before any change to the facts, the instructions or the model, and for each provider; keep the question set in step with the sample (`npm run test:new` says when a question lost its fact). Next in the plan: Ask Avala across the platform (parked until after the release; see the plan), the gap-closing interview, then proposals a person confirms.

## Error monitoring

Sentry (free Developer plan: one user, 5,000 errors a month). `journey/monitoring.ts` loads `@sentry/react` only when the build has `VITE_SENTRY_DSN` (set in Netlify's environment), errors only: no session replay, no performance tracing, console breadcrumbs dropped. Every report goes through `scrubEvent` (`domain/site/errors.ts`): no user, no extra data, addresses without query or fragment (where reset and unsubscribe tokens travel), and email addresses, JSON Web Tokens and long keys removed from text. `journey/ErrorBoundary.tsx` wraps every page: a screen that fails to draw is reported and shows "Something went wrong" with Reload. The privacy notice lists Sentry. The edge functions are not monitored yet (their errors are in the Supabase logs).

## Backups

The Supabase project is on the Free plan, which keeps no backups, so `.github/workflows/backup.yml` makes one every night (02:11 in India): `pg_dump` of the schemas `public` and `app_private` and of `auth` (the accounts), encrypted with gpg (AES-256) and kept as a workflow artifact for 30 days, then restored into a throwaway Postgres 17 where every table must come back with the row count it had live; a failed run emails the repository owner. The repository is public, so the dump is only stored encrypted and the log shows totals and table names, never data. Secrets: `SUPABASE_DB_URL` (the Session pooler connection string) and `BACKUP_PASSPHRASE` (long and random, kept outside GitHub too); without them the job says so and stops. Not in the dump: Vault secrets (AI keys are re-entered after a restore into another project), the pg_cron schedule (re-run that part of migration `needs_email`). Scheduled workflows run only from `main`, so it starts with the next release. The restore steps are at the top of the workflow.

## Homepage

`/` is the public homepage (`journey/home/HomePage.tsx`), loaded without the application or the database client; every other unknown path still goes to My work. A signed-in visitor (a Supabase session key in local storage) sees "Open my work" instead of "Sign in".

Every screen on it is the product itself, not a mock-up. `tests/e2e/tour.spec.ts` runs the sample case (`eval/corpus/ap-invoice`, a made-up company; its hand-checked model stands in for extraction, which needs the server) through every stage and captures the screens; CI prints them in the browser job log on `claude/` branches. The sample's facts that only its people could give (SAP worked through its screens, rules written down, only invoice reading needs AI) are entered by that test in the product's own Inputs view, and its team is named on the process; the result the page quotes (RPA-led, 15 of 20 steps by rules, 1 needs AI, 4 stay with people) is what the product then computes, so update the page's wording if the sample or the scoring tables change. To refresh the tour after the product's look changes, take the `tour-*.jpg` screens from that log and convert them into `public/marketing/tour/*.webp` (2000 px wide; the three `reason-*` images are crops). Keep the claims on the page to what the product does, and keep the line that says the screens are a sample case.

Two sections are built from the product's own lists so they cannot claim more than it does: "Start with one part, or use it all" (`#start`, the four set-ups from `PLANS` in `domain/workspace/modules.ts`) and "Your AI, your key" (`#ai`, the providers from `AI_PROVIDERS`: only those with `checked` are called available, the rest "coming once each passes our extraction check"). Setting `checked` on a provider moves it on the homepage too. The main navigation (`SiteNav`) shows its links on wide screens and behind a Menu button on narrow ones.

The tour runs five stages of six seconds (about 30 seconds), two screens each with a slow zoom. A stage's progress bar is a CSS animation whose end advances the stage, so pausing the animation pauses the timing. With reduced motion nothing runs on its own and both screens of a stage are shown one under the other. Test: `tests/e2e/home.spec.ts`.
